# Recursive Blake leaf verifier mishandled one full block

## Classification

- Confirmed historical verifier-binary completeness bug
- Boundary: Merkle leaf bytes → Blake2s digest inside the alternative-compression recursive verifier
- Component: full-round/final-round scheduling for exact-block inputs
- Security character: the recursive verifier implemented a different hash function on a boundary length
- Fixed by: [`0e81150`](https://github.com/matter-labs/zksync-airbender/commit/0e81150273f40637cd926296139f254a2ac64957)
- Vulnerable revision: `62e23e7cb573251298e9cbb7852e80124fc2c0ba`

## Boundary context

Blake2s marks the last compression specially. For an input whose length is an exact block multiple, the last full block must be removed from the ordinary-round count and processed once as the final block. The alternative-compression implementation is security-sensitive because it is used by a recursive leaf-inclusion verifier and must agree byte-for-byte with the native/prover commitment implementation.

The one-block case is the smallest exact-multiple boundary:

```text
input length       = BLOCK_SIZE
initial full rounds = 1
initial tail length = 0
correct schedule    = 0 ordinary rounds + 1 final full block
```

This boundary was reachable: generated unrolled circuit verifiers selected the
alternative-compression implementation by default on RISC-V, and several
committed setup-tree layouts had `total_width = 16` u32 words, exactly one
Blake2s block.

## Failure

When the tail length was zero, the implementation changed it to a full-block final round. It decremented `num_full_rounds`, however, only when the count was greater than one. At exactly one block the decrement was skipped, leaving both one ordinary full round and one full final round in the schedule.

The off-by-one is easy to miss because non-multiple inputs already have a distinct partial final block, while exact inputs of two or more blocks took the decrement branch.

## Failure flow

1. Supply a Merkle leaf/preimage whose encoded length is exactly one Blake2s block.
2. The recursive verifier computes `num_full_rounds = 1` and `last_round_len = 0`.
3. The exact-multiple branch promotes the tail to a full final block but fails to remove it from the ordinary count.
4. The alternative-compression path hashes a schedule different from standard Blake2s/native commitment construction.
5. A valid native authentication path fails recursive verification, or a path built under the alternate hash is interpreted differently at another verification boundary.

This is an implementation-parity/completeness failure: canonical setup leaves of
the affected width hash to a different digest and valid native authentication
paths are rejected. The history does not establish a Blake collision or an
invalid path accepted against a canonical native root, so it is not classified
as soundness.

## Impact and fix

Recursive Merkle verification hashed the exact-one-block boundary differently from the prover/native verifier. The fix changes the guard to `num_full_rounds > 0`, so any exact nonempty multiple moves its last block from ordinary processing to final processing exactly once.

Hash gadgets and verifier binaries should be tested as implementations of a shared byte-level function, not merely against examples generated by the same buggy implementation.

## Regression

- Compare standard, native, recursive, and alternative-compression digests at lengths `0`, `1`, `BLOCK_SIZE-1`, `BLOCK_SIZE`, `BLOCK_SIZE+1`, `2*BLOCK_SIZE`, and `3*BLOCK_SIZE`.
- Check both raw digest equality and acceptance of the same Merkle authentication path/root.
- Assert that every nonempty message has exactly one final compression and that no block index is processed twice.
- Include the actual encoded leaf lengths used by every supported Merkle tree/domain.
