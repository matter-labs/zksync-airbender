# Boundary check read the wrong grand-product column

## Classification

- Confirmed historical generated STARK verifier soundness bug
- Component: first/last-row quotient constraints for the memory grand product
- Reduction location: AIR boundary constraints → quotient numerator → DEEP/FRI composition
- Security character: intended accumulator endpoints were unpinned in the generated verifier
- Fixed by: [`16b5aef`](https://github.com/matter-labs/zksync-airbender/commit/16b5aefcd6210859c5c281b8189ab366fe2b8411)
- Vulnerable revision: `1826de4ad588f6d14198bac8ee170993f503df81`

## Protocol context

The legacy STARK memory argument uses a stage-2 grand-product column. Its transition relation constrains how the accumulator evolves row by row, while separate first/last-row constraints pin the multiplicative normalization and the exported final accumulator.

The quotient evaluator divides each boundary numerator by the corresponding first- or last-row vanishing factor and batches it with `quotient_alpha`. If the numerator reads another column, FRI can prove a perfectly low-degree quotient for the wrong AIR.

## Intended quotient relation

Let `Z` be the grand-product accumulation column selected by layout metadata:

```text
first row: Z(ω^0) - 1 = 0
transition rows: Z(next) * denominator - Z(current) * numerator = 0
last row: Z(ω^(N-1)) - expected_final_accumulator = 0
```

Both boundary constraints must resolve `Z` through the same symbolic stage-2 layout accessor used by prover and circuit generation.

## Failure

The generated quotient code hardcoded stage-2 column `50` for both initial and final memory grand-product boundary checks. After a layout change, the actual accumulation polynomial moved to column `51`.

The verifier therefore constrained an unrelated stage-2 polynomial at the endpoints while leaving the real accumulator's initial/final values unchecked. Transition constraints alone generally retain a multiplicative normalization freedom and do not establish the public/global product endpoint.

## Adversarial flow

1. Supply stage-2 column 50 values satisfying the mistakenly generated boundary numerators.
2. Choose the true accumulator column 51 with endpoint values not equal to `1`/the exported final product.
3. Satisfy its row transition recurrence under the unconstrained normalization or otherwise target the wrong memory relation.
4. Construct quotient parts for exactly the expressions generated by the verifier.
5. Pass DEEP/FRI because those layers authenticate the wrong quotient polynomial, not the omitted intended constraint.

Whether a complete forgery exists depends on all remaining memory/public-output constraints, but the generated verifier plainly failed to enforce the specified endpoint polynomial. This is stronger than honest-prover mismatch because the verifier's accepted AIR itself was wrong.

## Impact and fix

The intended memory accumulator boundary was absent from the generated acceptance relation. The fix calls `get_intermediate_polys_for_grand_product_accumulation_absolute_poly_idx_for_verifier()` and regenerates the inlined verifier, moving both reads to column 51 for that layout.

Generated indices are security-critical. Audit the generator and emitted artifact, and require symbolic column identities to survive layout changes rather than freezing numeric offsets in templates.

## Regression

- Mutate the true initial and final accumulator independently and require quotient failure.
- Mutate the neighboring column formerly at offset 50 and confirm it does not substitute for `Z`.
- Structurally compare every generated boundary read with its layout accessor.
- Regenerate after inserting a stage-2 column and require semantic constraints to follow the moved polynomial.
- Check both generator output and the verifier binary/artifact actually selected in tests/deployment.
