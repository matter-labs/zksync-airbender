# WHIR: Opening-proof construction

> The polynomial-commitment opening proof that discharges the GKR base-layer claim:
> the message order of one round, the oracle and leaf geometry, and how the paper's
> round indexing maps onto the production round boundary. This module carries no
> numbered claims; the enforceable obligations are in [verifier.md](verifier.md).

## Imports

- `protocols/sumcheck/verifier.md`
- `protocols/transcript/verifier.md`

## Guarantee

Acceptance reduces one batched evaluation claim about the committed base-layer oracles
to the explicit final polynomial, which the verifier then evaluates directly at every
point the reduction accumulated.

## Symbols

- `F` — base field; `E` — the field challenges and folded values live in: the
  degree-four extension of `F` below L1, and `F` itself on the L1 path.
- `m ∈ [1, ∞)` — variables of the committed multilinear message polynomial.
- `M ∈ [2, ∞)` — the number of WHIR rounds, indexed `i ∈ [0, M)`. Round `0` is the
  initial round and round `M − 1` the final round.
- `k_i ∈ [1, m]` — variables folded in round `i`, with `Σ_(i=0)^(M-1) k_i ≤ m − 1`.
- `m_i = m − Σ_(j<i) k_j` — variables of the polynomial entering round `i`; `m_0 = m`
  and `m_M = m − Σ_i k_i ∈ [1, 4]` is the plaintext tail.
- `rho_i ∈ [0, ∞)` — log2 of the LDE factor of the oracle read in round `i`.
- `L_i` — the round-`i` evaluation domain: the smooth multiplicative coset of order
  `2^(m_i + rho_i)` generated by a `2^(m_i + rho_i)`-th root of unity.
- `f_i : L_i → E` — the round-`i` oracle. `f_1, …, f_(M-1)` are committed; `f_0` is not,
  see below.
- `a_i ∈ E^(k_i)` — the `k_i` Sumcheck coordinates drawn in round `i`.
- `g_i = Fold(f_i, a_i)` — `f_i` folded at `a_i`, a function on the coset quotient
  `L_i^(2^k_i)`, whose order is `2^(m_i + rho_i - k_i)`.
- `h_(i,l)` — the round-`i`, step-`l` Sumcheck message: `3` coefficients of `E`.
- `z_i ∈ E`, `y_i ∈ E` — the out-of-domain point and reply for `f_i`.
- `t_i ∈ [1, ∞)` — queries drawn in round `i`, all of them into `f_i`.
- `u_(i,j) ∈ [0, 2^(m_i + rho_i - k_i))` — the query index of query `j` of round `i`;
  `x_(i,j) ∈ L_i^(2^k_i)` — the domain point it names.
- `gamma_i ∈ E` — the round-`i` delinearization challenge.
- `gamma_whir ∈ E` — the base-oracle batching challenge supplied by GKR.
- `pow_i` — proof-of-work bits verified in round `i`.
- `cap_i` — the Merkle cap committing `f_i`; `c` — log2 of the cap size.
- `z ∈ E^m` — the opening point of the incoming GKR claim.
- `P_1, …, P_ell` — the committed base-oracle columns, `ell` of them.
- `f_M` — the final polynomial, multilinear in `m_M` variables, sent in the clear.
- `pow(x, n) = (x, x^2, x^4, …, x^(2^(n-1))) ∈ E^n` — the multilinear point that one
  element of `E` denotes.
- `eq(y, w) = y · w + (1 − y)(1 − w)`, extended coordinatewise to points.
- `pack ∈ [0, ∞)` — log2 of the column-packing factor of the selected profile.

## The message polynomial and the base oracle

WHIR tests one polynomial, the `gamma_whir`-weighted combination of every committed base
column:

`f_0 = Σ_(n=1)^(ell) gamma_whir^(n-1) · P_n`.

No oracle is committed for `f_0`. The base columns are committed in `2` or `3` Merkle
trees, one per oracle class in memory, witness, setup order, each with its own cap and
its own `Σ`-offset into the powers of `gamma_whir`; a merged base commitment carries the
memory and witness columns in one tree with the witness columns after the memory ones.
A query into `f_0` therefore opens one leaf per tree at the same query index and combines
the opened values at read time. This is the project's virtual-oracle construction at
one shared point `z`; its soundness reduction is `GAP-WHIR-SND-001`.

On the L1 path the message is instead `2^pack` base columns interleaved into one
polynomial, so `m = (log2 trace length) + pack` and a base leaf holds `2^(k_0)` elements
per packed column group. Below L1 `pack = 0`.

## Round messages

Round `i ∈ [0, M − 1)`, in wire order:

1. `k_i` Sumcheck steps. For `l ∈ [1, k_i]` the prover sends `h_(i,l)`; the verifier
   absorbs it and draws `a_(i,l)`.
2. The prover sends `cap_(i+1)`; the verifier absorbs it.
3. The verifier draws `z_(i+1) ∈ E`.
4. The prover sends `y_(i+1) ∈ E`; the verifier absorbs it.
5. The prover sends the `pow_i` nonce; the verifier verifies it.
6. The verifier draws `u_(i,1), …, u_(i,t_i)`.
7. The verifier draws `gamma_i`.
8. The prover sends, per query, one leaf of `f_i` and its Merkle path.

Round `M − 1`, in wire order:

1. `k_(M-1)` Sumcheck steps, as above.
2. The prover sends `f_M` as `2^(m_M)` coefficients of `E`; the verifier absorbs them.
3. The prover sends the `pow_(M-1)` nonce; the verifier verifies it.
4. The verifier draws `u_(M-1,1), …, u_(M-1,t_(M-1))`.
5. The prover sends, per query, one leaf of `f_(M-1)` and its Merkle path.

Round `i` reads `f_i` and commits `f_(i+1)`, so the final round commits no oracle and
draws neither an out-of-domain point nor a delinearization challenge. One proof
therefore carries `M − 1` committed caps, `M − 1` out-of-domain samples, `M − 1`
delinearization challenges, `M` proof-of-work stages, `Σ_i t_i` queries, and one
explicit polynomial.

The baseline groups a round as "send the folded oracle, sample out of domain, sample
shift queries, then run that oracle's Sumcheck". Production cuts the round one step
earlier, so the Sumcheck steps of a round precede the commitment of the next oracle.
The wire order is the same; only the labels differ. Where the baseline writes
`gamma_(i+1)` for the challenge that weights the queries into `f_i`, this module writes
`gamma_i`.

## Oracle and leaf geometry

| Oracle | Domain order | Leaf contents | Tree leaves | Path length |
|---|---|---|---|---|
| base, per tree | `2^(m + rho_0)` | `2^(k_0)` elements of `F` per column of that tree | `2^(m + rho_0 - k_0)` | `m + rho_0 - k_0 - c` |
| `f_i`, `i ∈ [1, M)` | `2^(m_i + rho_i)` | `2^(k_i)` elements of `E` | `2^(m_i + rho_i - k_i)` | `m_i + rho_i - k_i - c` |

A leaf holds one whole `2^(k_i)`-element coset of `L_i`, so the `t_i` queries of round
`i` each read a single leaf and the verifier folds it locally to one value of `g_i`.
Below L1 the initial fold is `k_0 = 1`, so a base leaf holds exactly two values per
column.

The domains are not forced to shrink. Each `L_i` is chosen by the selected parameter
set subject to `m_i + rho_i` not exceeding the field's two-adicity, so the rate
`2^(-rho_i)` improves across rounds and the query count falls with it. That rate
improvement, not domain halving, is what distinguishes this construction from a
FRI-style query loop.

## Accumulated weight

The reduction never discharges an out-of-domain reply or a query in the round that
produced it. Round `i` folds its `1 + t_i` new constraints into the claim entering round
`i + 1`,

`claim_(i+1) = claim_i' + gamma_i · y_(i+1) + Σ_(j=1)^(t_i) gamma_i^(j+1) · g_i(x_(i,j))`,

where `claim_i'` is the terminal Sumcheck claim of round `i` (`OUT-SUM-VER-001`), and at
the same time appends them to a weight polynomial that only the final check of
`REQ-WHIR-VER-010` discharges. Every accumulated constraint has the form
`Z · eq(p, X)`: the initial claim contributes `p = z` with coefficient `1`, the
out-of-domain reply of round `i` contributes `p = pow(z_(i+1), m_(i+1))` with
coefficient `gamma_i`, and query `j` contributes `p = pow(x_(i,j), m_(i+1))` with
coefficient `gamma_i^(j+1)`. The final round's queries are the exception: they are
checked by direct equality against `f_M` and are not accumulated.

## Data flow

```text
batched GKR base-layer claim at z, with gamma_whir
  → round 0: k_0 folds, commit f_1, out-of-domain, nonce, queries into the base trees
  → rounds 1 .. M-2: the same body, queries into f_i
  → round M-1: k_(M-1) folds, explicit f_M, nonce, queries into f_(M-1)
  → direct equality at every final query, then the accumulated weighted sum
```

## Open boundary

- The concrete `M`, `k_i`, `t_i`, `rho_i`, `pow_i`, cap size, and `pack` of a profile are
  selected in [soundness parameters](../../soundness/parameters.md), not here. No value
  of the schedule is carried by a proof.
- Batching across several committed roots is expressed by the GKR handoff claim and by
  the read-time combination above, not by a WHIR-internal multi-root construction.
