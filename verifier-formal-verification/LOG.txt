=== PROCESS ===
- SPEED / RAM (user, 2026-10-12): "loops that take minutes are wrong; everything must be fast, modular, baby steps;
  don't run things that use a lot of RAM". Working conventions chosen by the agent (not user rules): aim for a few
  seconds per Lean file (~10 s is a soft target, not a reason to split on its own), hard kill at 60 s and ~4 GB
  (lean/check.sh: timeout + cgroup; `ulimit -v` breaks Lean's threads). Minutes = design bug, not a wait.
  Work in baby steps: one small lemma/file at a time, measure it, then combine. Never rebuild the Sail model casually.
- RULE OF THUMB (user, 2026-10-13): whenever large data or many cases are involved (big symbolic states, long
  tables, many instructions), avoid anything whose cost grows with that size: unfolding definitions, "by
  computation" steps (rfl / decide / kernel evaluation on big terms), re-deriving the same fact at every step.
  Instead prove small general lemmas once (on a tiny variable state / one entry / one instruction) and use them
  as ordinary rewrites, so each use costs the same however big the data is.
  Examples so far: state-accessor lemmas proved by `Eq.trans rfl rfl` (not `rfl`); register-read simproc instead
  of if-chains; per-word decode lemmas; table entries read by `table_read`; link check as one list equality
  instead of per-word evaluation; loops by one-iteration lemma + induction (never unrolled).
